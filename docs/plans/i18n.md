# Internationalisation: English, French and Spanish, on the controller and in Home Assistant

Tracking document. One session per work package (WP). Planned against main at v1.9.0 on 2026-11-19.

## Branches

The feature lives on **`feat/i18n`**, branched from main. Nothing reaches main, and so no release or controller update happens, until the whole feature is ready. This plan, the VERSION bump (1.10.0 then, 1.11.0 now) and the Claude rule (`.claude/rules/translations.md`) are its first commit.

```
main ── feat/i18n ──┬── feat/i18n-i1-firmware-codes ──┐
                    ├── feat/i18n-i2-core ────────────┤ PRs into the feature branch
                    ├── … i3-card, i4-page, i5-ha, i6-install, i7-docs ─┘
                    └── one PR into main = one release = the update
```

To claim a WP:
1. Check `gh pr list --base feat/i18n` and the table below.
2. Branch from `feat/i18n` as `feat/i18n-i<n>-<topic>`. In the first commit, set its row to `in progress` with the branch name.
3. Open the PR **into `feat/i18n`**, not main. The PR that finishes the WP sets its row to `done` and links itself.
4. Merge it once CI is green. Then the next WP that depends on it merges the feature branch in.

The feature branch's other rules are those of [optional-fill-meter.md](optional-fill-meter.md):
- **Version:** VERSION is 1.11.0, the next unreleased minor. It was 1.10.0 until main released that one first (the page login, 2026-11-19); the sync of main into I2 bumped it (2026-11-20). If main releases another minor first, the next sync bumps it again. release.yml's check runs on every PR, whatever its base, so the sub-PRs don't each bump it.
- **Keeping up with main:** merge main into the feature branch whenever main moves, at least before the final PR. Then each open WP branch merges the feature branch in. **Any user-facing text a merge from main brings in is translated in that merge** (or listed under I7 if its file's WP is already done), so nothing French-only reaches the release.
- **Going live:** when every WP is `done`, one PR from `feat/i18n` into main. Its merge releases 1.11.0: controllers see it through their Firmware update entity, HACS offers the card.
- **Mid-feature testing:** `make ota` from the feature branch (development build), never through a release.

## Why

Today the whole interface is French:
- the card;
- the controller's page and its setup wizard;
- the dashboard, the scripts and the blueprint's texts;
- some of the firmware's states.

The install page says the wizard is « in French for now ». The firmware is generic and published (secret-free firmware), so anyone can install it. The interface should speak English, French or Spanish, picked from the viewer's own language, with no internet connection needed.

## Decisions (2026-11-19)

- **Languages: English (`en`), French (`fr`), Spanish (`es`).**
  - Anything else falls back to English.
  - Adding a language means adding one dictionary per surface and its HA files, with no code change (I7 documents how).
- **The firmware publishes codes; the UIs translate them** (choice A of the options review).
  - One firmware serves every language, and adding a language needs no OTA.
  - The cost: HA's device page shows the codes as they are (`up_to_date`, `on_request`). This was accepted.
  - No per-language firmware builds and no Language setting on the device.
- **Entity names stay English, and no entity id ever changes.**
  - ESPHome sends names to HA as plain text: they can't follow the HA user's language.
  - Their ids are what the card, the dashboard, the scripts, every install's automations and the recorder's history hang on.
  - The two French-named sensors (« Piscine - Débit remplissage », « Piscine - Volume total remplissage ») keep their names for the same reason.
- **Values that are already codes stay as they are:**
  - `Auto`/`Off`/`Low`/`Medium`/`High` (Manual Override, and the scripts' `vitesse`);
  - `Connected`/`Hotspot`/`Connecting`, `SNTP`/`Browser`, `configured`, the Setup State items, Schedule Waiting For's words, Fill Meter Status;
  - the placeholders `--` and `--:--`.
  Changing them would break automations for nothing. Only French prose becomes codes (I1's contract).
- **Fully local.**
  - Every dictionary is built into what runs: the controller's page (in its flash) and the card (in its HACS file).
  - The language is read from the browser or the HA profile. Nothing is fetched to translate.
  - The page in particular must work in all three languages on the controller's hotspot with no internet (the setup wizard runs there).
- **Language selection:**
  - **Card:** the HA user's profile language (`hass.locale.language`, else `hass.language`), unless the card's optional `language: en|fr|es` setting forces one.
  - **Controller's page:**
    - the first of the browser's `navigator.languages` that is `en`, `fr` or `es`;
    - an EN | FR | ES switch on the page (header, and the wizard's first step) overrides it, remembered in `localStorage` (wrapped in try/catch, the browser's language when unavailable);
    - the page hands its language to the card through its HA stand-in (`esphome-hass.js` sets `hass.locale`), so the card has one code path.
- **Formatting follows the full locale** (`fr-FR`, `en-GB`, `es-ES`, or the browser's own tag), through `Intl`, never a hard-coded `"fr-FR"`.
  - The card also honours HA's `locale.number_format` and `locale.time_format` (12/24 h).
  - Units the firmware publishes (L, min, h, °C) stay as they are. Abbreviations the UI writes come from the dictionary: `7 j` in French, `7 d` in English and in Spanish (días).
- **Mechanism: a small in-house helper, no library.**
  - `t(key, vars)`: `{name}` placeholders, plurals through `Intl.PluralRules` (`key.one` / `key.other`), and English when a key is missing (a test makes sure none is).
  - Semantic keys (`card.pump.stopped`), not French sentences as keys.
- **Dictionaries are JSON, one file per language per surface:**
  - `home-assistant/i18n/{en,fr,es}.json`: the card and the firmware codes. The device page uses them too, through the card.
  - `webui/i18n-page/{en,fr,es}.json`: the page and its wizard only, so HA's card doesn't carry the wizard. (`webui/i18n` and `webui/i18n.js` are symlinks to the card's, like `webui/piscine-card.js`, so the card's imports resolve when the mock serves `webui/` unbundled.)
  - the install page keeps its own small dictionaries (`docs/install/i18n/`), since GitHub Pages serves that folder alone;
  - `home-assistant/i18n-yaml/{en,fr,es}.json`: the texts of the Home Assistant files (dashboard, scripts, blueprints), from which those files are generated (below).
  - `tools/i18n/surfaces.mjs` lists these surfaces, with where each one's keys are used; the checks, the export and the import read it.
- **The card gets a build step for its release** (agreed): esbuild, already used for the page, bundles `home-assistant/piscine-card.js` and its dictionaries into the release asset, **minified** (2026-11-19), still named `piscine-card.js` (HACS's `filename`).
  - The source stays the single card file, and `const VERSION` stays in it for release.yml.
  - The dictionaries are imported as JSON modules (`import en from "./i18n/en.json" with { type: "json" }`), which esbuild bundles. The card preview (Chromium) and `node --check` also load them unbundled.
- **Home Assistant files: one per language, generated** (2026-11-19, so their texts go through the translation tool with the rest).
  - Each file has one template (`*.tmpl.yaml`) where a text is `{{t:key}}`, and its texts in `home-assistant/i18n-yaml/`. `make ha-files` writes one file per language from them. The generated files are committed, since users copy them from GitHub, and a check fails when one is out of date.
  - So the language files of a set have the same structure by construction, and only their texts differ.
  - `home-assistant/dashboard/dashboard.<lang>.yaml` and `scripts.<lang>.yaml` replace `dashboard.yaml` and `scripts.yaml`.
  - The scripts' ids and fields (`piscine_forcer_vitesse`, `piscine_retour_auto`, `vitesse`, `duree`) are the card's API and are identical in every language; only `alias`, `description` and field `name`s are translated.
  - Blueprints: `pool_fill_too_long.yaml` stays the French one, because every imported copy's `source_url` points at that path and HA re-imports from it. `pool_fill_too_long.en.yaml` and `.es.yaml` are added. Each has its texts and defaults, including the phone's « Acquitter » action title, which becomes an input.
- **Everything is translated, product terms included** (2026-11-19). The speeds and « Override », which today's French UI keeps in English, get a word in each language (glossary in I2). Only codes stay as they are: what the firmware publishes, and the values the scripts take (`vitesse: Low`). A label shows the translated word, and the card sends the code.
- **French changes only by the glossary, or by the owner.** `fr.json` holds today's French verbatim, apart from the glossary terms now translated and the texts the owner re-translates through the tool (2026-11-20: the picker's name and description, the filtration section's title). I3 and I4 compare `make card-shots` and the mock's screenshots in French, before and after: each difference must be one of those.
- **Translation workflow** (2026-11-19). There is no Spanish speaker on hand, so the translations go through a machine-translation tool (the owner uses Lokalise). The export is plain Markdown, not tied to any tool (2026-11-19):
  1. Claude writes `en`, `fr` and `es` with each change (the Claude rule), so every merge is complete in three languages.
  2. Before the release, `make i18n-export` writes every dictionary (card, page, install page and Home Assistant files) to one Markdown file in English, the source language: one paragraph per text, its id alone in an HTML comment above it.
  3. The owner runs that file through the tool, which returns a Spanish Markdown file.
  4. `make i18n-import TO=es FILE=…` reads it back into the `es` dictionaries. It refuses an entry whose placeholders or plural forms changed, or a glossary term translated another way (the tool doesn't see the glossary), and lists every value that differs from Claude's draft, for a look in the PR.
  The owner reviews the French. The same round-trip works for any later language.
- **Docs stay English.** UI labels are quoted in English with the French in brackets: « Settings » (« Réglages »).

## Firmware code contract (I1)

Agreed up front, so the card, the page and the mock can proceed before the firmware. Only these states change.

| Entity | Today | Codes |
|---|---|---|
| Update Status | `non vérifié`, `vérification`, `à jour`, `disponible`, `installation`, `en attente (mode manuel)`, `en attente (remplissage)`, `erreur (vérification)`, `erreur (installation)` | `unchecked`, `checking`, `up_to_date`, `available`, `installing`, `pending:override`, `pending:fill`, `error:check`, `error:install` |
| Update Check Interval (select options) | `À la demande`, `6 h`, `24 h`, `7 j` | `on_request`, `6h`, `24h`, `7d`. The choice is stored as hours (`update_check_hours`), so it survives the OTA. An HA automation that picks an option by its French text must be updated, which the release notes say. |
| Fill Water Import (result written back to the text) | `importé : N jour(s)`, `importé : N mois`, `refusé : pas d'heure`, `refusé : <French reason>` | `imported:days:N`, `imported:months:N`, `refused:no_clock`, `refused:format`, `refused:date`, `refused:value`, `refused:too_many`, `refused:future`, `refused:record_ahead` |
| Last Recomputed At | `Never` | `--`, like every other "not yet" |

- Codes are ASCII, lower snake case, with `:` before an argument.
- The UIs translate them through `status.<entity>.<code>` keys.
- An unknown code shows as is, never as an empty line.
- **Skew:** the HACS card can run against an older firmware, and the reverse.
  - The card maps the old French states to the codes (`LEGACY_STATUS`, one table, removed once no supported firmware sends them: noted in I7).
  - An older card on a newer firmware shows the raw code in the update line, which is readable, and the two are released together anyway.
  - The page is built into its firmware, so it never skews.
- Log messages (`ESP_LOGx`) stay English and aren't translated.
